# Private backend operations and recovery

These are review templates, not an installed deployment. All validation uses generated credentials, synthetic evidence and uniquely named disposable resources. Obtain owner approval before any deployment, real credential change, backup/restore, production data access or publication. Nothing here grants intelligence publication authority. Private coordinates, source files, source provenance and offline history remain outside images, Git, public builds and CI artifacts.

## Installation and trust boundaries

Use Python 3.12 and free/open-source Docker Engine/Compose, Nginx, OpenSSL, PyMongo and cryptography. The explicitly requested MongoDB Community database is free/source-available under SSPL, not an OSI-approved open-source license; review its obligations before redistribution or offering a database service. In a dedicated approved environment install `backend/requirements-dev.txt` and `operations/requirements.txt` with `pip install --require-hashes -r ...`. The operational encryption dependencies are separate from the minimal backend runtime image. No paid service or new hosted infrastructure is required.

`deployment/secure/compose.yaml` is configuration for review. Parse it with `docker compose --env-file /dev/null -f deployment/secure/compose.yaml --profile local-replica config --quiet` after setting `WATCHDAWG_SECRETS` and `WATCHDAWG_AUDIT` to private absolute paths; this does not start services. Never point the disposable test runners at a real database: they have no production connection option.

Only the TLS proxy publishes a port, on host loopback `127.0.0.1:8443`. The backend/API and MongoDB data networks are internal; a separate proxy-only ingress bridge permits the loopback port mapping. Docker does not publish ports on internal-only networks. Backend and MongoDB publish no ports and have no outbound Internet route. Connect through an approved private host tunnel/interface; do not change to `0.0.0.0` casually. Enforce deny-by-default proxy egress and the equivalent host firewall, IPv6 and Docker forwarding rules on the actual host; Docker administrator access bypasses these controls. The proxy reaches only the backend network, MongoDB only the data network, and backend connects to both. Reserve the template subnet `172.30.10.0/29` or review conflicts and update the complete policy together. `watchdawg_backend` is the backend network alias used by Nginx.

Containers run as UID 101 (proxy), 10001 (backend) and 999 (MongoDB), read-only with all Linux capabilities dropped and no-new-privileges. Provision writable private audit storage separately, UID 10001 mode 0700. Secret directories are 0700, with files owned by the consuming UID, mode 0400/0600. Bind secret directories read-only; mount the directory rather than an individual policy file so an approved atomic rename is visible. Never use secret values in Docker arguments, environment variables, Git, URLs in documentation, public artifacts or logs. Obtain and store credentials through an approved private channel.

Required proxy files: `server.crt`, `server.key`, `backend-ca.crt`, `proxy-client.pem` (combined certificate and key). Backend files: `backend.crt`, `backend.pem`, `backend-ca.crt`, `ca.crt`, `client.pem`, `mongo-uri`, `security.json`. Each MongoDB member needs its `node.pem`, `ca.crt` and shared replica authentication `repl.key`. Use independently scoped server/client certificate trust and owner-approved issuance/renewal; the ephemeral CA helper in `operations/tls.py` is for disposable tests only. Do not use its one-day certificates in production. Private keys and backup encryption keys require separate escrow and compromise procedures.

Nginx permits TLS 1.2/1.3 only, fixed host `watchdawg.internal`, and only the existing health/audit API routes. It verifies the backend certificate name `watchdawg-backend.internal` and CA and supplies a client certificate. Uvicorn requires a verified client certificate; MongoDB requires TLS with verified CA/hostname and client certificates as well as database authentication. There is no plaintext fallback, insecure certificate option or automatic upstream retry. Certificate errors must cause failed requests, never verification bypass. An upstream server certificate must contain the exact configured DNS SAN; MongoDB certificates need all approved replica DNS names. Backend configuration deliberately disables providers because the isolated template has no Internet route. Enabling any live provider requires an approved egress design and separate privacy/conformance review.

Generate policy offline using `scripts/create_backend_security.py` with `--transport proxy --host watchdawg.internal --network 172.30.10.2/32 --proxy-network 172.30.10.2/32` and explicitly approved principal IDs/scopes. This only creates local files and does not install them. Use separate monitor (`health:read`) and analyst (`audit:run`) credentials. Never trust an entire client subnet or forwarded user identity. Uvicorn has `--no-proxy-headers`; Nginx overwrites proto and strips forwarded client IP/identity/request IDs. Backend uses the actual socket peer, not caller-supplied forwarding headers. Rate/stream limits are shared in MongoDB; overlapping tokens retain the same principal ID and HMAC identity. Review aggregate proxy-peer budgets, connection limits, private origin allowlists and CORS before installation.

## Credential rotation and compromise

The policy file is revalidated on every new request. Only principal credential/scope/expiry changes may reload; HMAC, rate, network, CORS or transport changes require a coordinated approved restart. Missing, unsafe, malformed or unexpectedly changed policy fails closed with 503. Keep the rate HMAC stable across workers and credential rotations. Do not run the bootstrap utility in place over an existing policy.

1. Stop and investigate on compromise; isolate ingress if necessary, preserve private audit records, and identify affected client/signer/database keys. Never paste token values into a terminal command or incident report.
2. For routine rotation run `python -m operations.cli rotate --policy PRIVATE_POLICY --principal APPROVED_ID --output-directory NEW_PRIVATE_DIRECTORY`. It exclusively creates a mode-0700 directory with a private token, overlap policy, final policy and hash receipt. Existing expiry must have at least 30 minutes remaining and there may be at most four hashes; rotation keeps the existing expiry and scopes. Schedule normal rotations well before expiry; renew expiry only after explicit access review.
3. Review the receipt privately. Use `install-policy --staged OVERLAP_JSON --target PRIVATE_POLICY --expected-sha256 PREVIOUS_DIGEST` from an interactive terminal. The command requires typing the exact installation confirmation. Compare-and-swap plus a private lock rejects stale planned changes, and fsync/atomic replacement avoids partial files. Install as the consuming UID through the approved secret-directory mount. All workers must see the same directory and hashes.
4. Deliver the new token privately, verify both credentials through the approved TLS endpoint, migrate every client, then install `final.json` using the overlap digest. Verify the old token returns 401, new token retains only approved privileges, and shared rate limits remain intact. Never print bearer headers in diagnostics.
5. For compromise, use `revoke --policy PRIVATE_POLICY --principal APPROVED_ID --output NEW_PRIVATE_FILE`, review and install with the current digest. It expires that principal without removing the final registry entry. Revoke all affected principals individually; expired entries keep authentication fail-closed. An admitted stream is not retroactively reauthenticated and can run for the existing 90-second provider bound; drain/stop affected workers or isolate ingress for immediate containment.
6. Never recover by reinstalling an older unrevoked policy. A trusted administrator can deliberately roll back files; CAS is stale-update protection, not a monotonic hardware revocation store. Preserve the latest revoked policy and independent receipt checkpoint. Recover a corrupt file with the latest reviewed revoked state, then issue a new separately reviewed credential. Rotate MongoDB, CA and reviewer keys separately as indicated by the incident; do not blindly restore compromised secrets from backups.

## MongoDB least privilege and failover

Provision a dedicated database, collections and replica set using a separately authorized administrator, never the application credential. `operations.mongo_roles.roles(database)` returns exact role documents; `provision` requires an explicit caller-supplied admin connection and validated >=32-character high-entropy passwords. It does not discover a URI, store passwords, grant admin or update existing users/roles. Reruns and interrupted administrative provisioning require human inspection, not automatic destructive reconciliation.

The app may insert only into `ai_audit_messages`, and find/insert/update/createIndex only in `security_windows` and `security_leases`. It cannot read financial messages or archaeological collections, modify/delete retained messages, drop databases or create users. The backup principal can find only retained audit messages. A temporary restore principal has insert-only access to a new isolated destination collection; remove its access after an approved restore. Security TTL cleanup concerns quota/lease state only, never evidence. Admin-provision required collections/indexes and audit retention separately.

Use a three-voter replica set, verified member DNS, TLS, keyfile authentication and majority writes. App readiness/security admission fails closed while a majority is unavailable; do not switch to standalone or in-memory quotas to regain availability. The optional `local-replica` profile is a same-host reference, not protection against host/disk/site loss; it is not automatically initialized or given users. Production must choose independent failure domains, storage, monitoring and backup consistency/RPO/RTO targets. Test election timing, rollback and clock behavior on the actual approved topology. Never force reconfiguration, promote a stale minority or reset security counters during a partition without incident-owner review.

The disposable runner verifies app role denials, successful majority writes, elected-primary failover, majority-loss 503/recovery and encrypted snapshot restoration to a uniquely named synthetic database. This is deterministic functional validation with bounded waits, not a claim of zero downtime or zero data loss on arbitrary infrastructure.

## Offline encrypted backup and restore

`python -m operations.cli keygen --output PRIVATE_EXTERNAL_KEY` exclusively creates 32 random bytes. Keep that mode-0600 key outside the source and separately escrowed from encrypted archives; losing the key loses recoverability. Do not commit or upload either item. Use a private mode-0700 destination on encrypted storage or tmpfs: the utility uses private plaintext ZIP scratch files and cleanup/unlink is not secure erasure on SSDs or snapshots.

`backup --source QUIESCED_PRIVATE_DIRECTORY --key-file PRIVATE_EXTERNAL_KEY --destination NEW_ARCHIVE` creates an exclusive AES-256-GCM archive plus a private ciphertext SHA-256 receipt. Stop all source writers first or take an approved consistent snapshot. Sources must be owned, regular, independent files in owned directories not writable by others. Symlinks/hardlinks, changing files and destinations inside the source are rejected. Sources, coordinates, evidence and original provenance are never rewritten or deleted. Archive/receipt publication is not a single transaction; preserve and investigate any incomplete pair after interruption, and never count it as a verified recovery point. Nothing automatically prunes backups or evidence.

`restore --source ARCHIVE --key-file PRIVATE_EXTERNAL_KEY --receipt RECEIPT --destination NEW_PRIVATE_DIRECTORY` verifies receipt, GCM authentication, complete manifest binding and per-file hashes before publishing a new private restore directory. Wrong keys, corruption, duplicate/traversal paths, existing destinations and expansion beyond bounds are refused. Restore publishes with Linux `renameat2(RENAME_NOREPLACE)` and refuses filesystems that lack atomic no-replace support. Use a supported local Linux filesystem for recovery and the synthetic drill. File bytes/provenance are retained, permissions normalize to 0600/files and 0700/directories; empty directories, timestamps and original permission metadata are not archived. Current snapshots are capped at 64 MiB and 4096 files, with bounded in-memory decryption. Large datasets need a separately reviewed sharding/streaming design; do not silently raise limits for production.

The database drill exports synthetic retained messages with a read-only user after a known sequence of writes, encrypts/decrypts and inserts into a fresh database with a distinct insert-only restore role. It is not an online consistent production database backup solution: metadata, indexes, all collections and concurrent-write consistency require a reviewed database-native snapshot procedure and separate restore validation.

`python -m operations.cli drill --workspace PRIVATE_DRILL_DIRECTORY` always generates its own synthetic fixture/key/archive and compares recovered bytes. It cannot select real evidence as input. `deployment/secure/restore-drill.service` and `.timer` are uninstalled systemd examples for a private dedicated local user, daily with jitter; review paths, dependency installation and private scratch allocation before owner-approved installation. No network access is required. Escalate a failed drill as an incident; never automatically promote a restore or publish intelligence. Perform a separately approved isolated real-data restore before accepting production recovery readiness.

## Durable private audit and retention

Outside explicit synthetic test mode the backend requires `BACKEND_AUDIT_DIR`. Its collector uses an owned dedicated 0700 directory, 0600 files, thread/process locks, fsync at admission and response, daily/size rotation, minimum retention and maximum segment count/size. It refuses an existing foreign evidence directory. Schemas allow only generated request IDs, HMAC principal references, fixed route aliases, timestamps and status/outcome. Credentials, peers, caller paths, bodies, coordinates, provider errors and evidence content are forbidden. Configure `BACKEND_AUDIT_SEGMENT_BYTES`, `BACKEND_AUDIT_MAX_SEGMENTS` and `BACKEND_AUDIT_RETENTION_DAYS` deliberately. Template limits are 64 MiB x 128 (8 GiB) and at least seven days. Reserve an additional >=10 MiB free space and filesystem/host quotas.

Only expired, recognized audit segments may be pruned; evidence/backup/reviewer records are never automatic cleanup targets. If capacity would require deleting unexpired logs, disk reserve is exhausted, storage is unsafe or a partial active tail is found, requests fail closed. An admission fsync occurs before provider/evidence work; an I/O failure after admission can interrupt a stream or prevent delivery after some work already happened, so correlate admission/outcome and investigate incomplete requests. Retention needs capacity planning against aggregate admitted and rejected traffic; size limits cannot guarantee seven days of high-volume service availability. Watch storage/permissions/segment count/ingress 503 externally using private monitoring and independent host telemetry. Do not health-probe at abusive rates when storage is full.

Nginx emits only a fixed privacy-safe schema; diagnostic errors are suppressed to avoid raw request/URI/token logging. Docker stdout has bounded 10 MiB x 3 rotation per service. Edge stdout is best-effort and may evict old events; the fsynced backend journal is the durable application collection. Neither journal is WORM or safe from a compromised host/same UID. Preserve encrypted offline copies and independently held hashes/checkpoints; stronger tamper resistance needs a separately approved independent custody design. Do not claim this local filesystem is an immutable legal archive. Minimum retention is governed by segment modification time; protect host clocks and filesystem metadata, and test recovery from clock rollback.

## Evidence and human review

Retain raw evidence, source identifiers/URLs, acquisition times, hashes and existing offline history under the existing evidence policy. No operational tool turns correlation, provider output or a review decision into a verified public intelligence claim. The existing private-permission migration utility remains dry-run by default; do not change real evidence permissions without the required reviewed migration plan.

`operations.review_records` appends Ed25519-signed, ordered, hash-chained private records binding evidence SHA-256, private reviewer-note SHA-256, reviewer ID and decision. The CLI requires a private reviewer key/registry and interactive `REVIEW <evidence hash>` confirmation. Decisions are only `reviewed_private`, `needs_more_evidence` and `rejected`; every record has `public_release_approved: false`. No route, scope, command, timer or webhook publishes anything. Evidence/notes stay in their original private custody; hashes and reviewer identities are also private metadata.

Store reviewer keys separately from application tokens; register keys through a reviewed private registry. Possession of a signing key plus interactive confirmation is an attestation, not proof of biological human presence. Verify signatures/chain and use `verify(..., expected_head=INDEPENDENT_CHECKPOINT)` to detect tail truncation/rollback. Preserve the latest head independently after each approved review; a hash chain alone cannot detect truncation. Archives/new review volumes need separately signed custody links and checkpoints. The journal caps at 16 MiB and refuses partial writes; no automatic reviewer-record deletion/rotation occurs. Rotate signer IDs with new keys and retain historical public-key trust/custody records; key compromise requires investigating affected attestations. Public release still requires a separate explicit authorized human decision and provenance verification outside these tools.

## Incident and disaster response

| Symptom | Containment and recovery (owner-approved real actions only) |
| --- | --- |
| 401 after rotation | Verify UTC expiry, intended principal and current private policy hash; deliver the approved new token. Never restore an old revoked token. |
| 403 / proxy mismatch | Check actual peer, exact allowlists, forwarding stripping and mTLS identity. Do not widen trusted networks or trust client-provided IP headers. |
| 502 / TLS failure | Check certificate chain, SAN, expiry, clock and permissions through private diagnostics. Renew through approved CA, validate before swap and drain/reload. Never disable verification. |
| 503 / policy or audit storage | Isolate abusive ingress; preserve policy/audit files and hashes. Restore the latest reviewed revoked policy, repair ownership or add approved storage. Never delete unexpired audit/evidence to recover capacity. Inspect incomplete tails privately; do not silently truncate them. |
| 503 / database quorum | Preserve volumes, establish which voters/data are current, restore network/TLS/member health and majority, then verify readiness and retained message hashes. Do not reset quotas or force a stale primary. |
| Credential or host compromise | Isolate, revoke affected credentials, drain streams, preserve encrypted forensic copies, rotate relevant CA/database/reviewer/backup keys from a clean environment, and review all actions since last trusted checkpoint. Rebuild from reviewed images; never trust a compromised host's restoration claims. |
| Host/site loss | Recover separately escrowed keys and latest verified offline backups/checkpoints to a new isolated host/database, validate provenance, signatures, counts and integrity with synthetic drills first. Reconcile post-backup evidence and compromised credential state. Have the owner approve cutover and recovery targets; do not connect restores to production automatically. |
| Key loss / failed integrity | Preserve all ciphertext and receipts unchanged; check approved escrow and earlier independent snapshots. Treat missing keys or unverifiable evidence as a blocker, never invent provenance or publish claims. |

After any incident, document private evidence custody, versions and timestamps, approved operator actions, observed data-loss window, failed/partial work and remaining uncertainty. Run the synthetic regression/recovery suites and an approved isolated recovery validation before considering a return to service. Deployment, integration, production access and intelligence publication remain separate approval decisions.
